● Guia do repositório

Como usar os dados

Este repositório baixa os microdados do BADEPI, organiza-os em camadas (bronze → silver → gold) e publica os painéis. Aqui está o modelo de dados de cada ativo, como rodar o pipeline, como consultar os parquet com pandas e como as derivações são calculadas.

Fonte

O que é o BADEPI

A Base de Dados de Propriedade Intelectual (BADEPI) é mantida pela Coordenação-Geral de Economia e Inovação do INPI em cooperação com a OMPI. Reúne, para fins estatísticos, os registros administrativos de cada ativo de PI, com série histórica de 2000 a 2025 e dados pessoais limitados conforme a LGPD. É atualizada uma vez por ano; a versão 12.0 saiu em 13/10/2026. Página oficial: gov.br/inpi → BADEPI.

São oito arquivos zip, um por ativo, cada um com CSVs (separador ;, CRLF, encoding misto latin-1/UTF-8, campos com espaços à direita) e um dicionário de microdados em XLSX. A tabela abaixo é lida da própria bronze e silver construídas por este repositório:

Arquitetura

Camadas medalhão

Bronze

Os zips e CSVs exatamente como o INPI publicou, com manifesto (URL, SHA-256, tamanho, data). Nada é alterado. data/bronze/<ativo>/

Silver

Parquet tipado e limpo: chaves sem espaços, datas reais, vazios como nulos, colunas derivadas (origem, via, situação) e dimensões para relacionamento. data/silver/<ativo>/

Gold

Agregações prontas para visualização em JSON pequenos, copiados para docs/data/<ativo>/ e servidos pelo GitHub Pages. data/gold/<ativo>/

Rodar

Do zero aos painéis em quatro comandos

Requisitos: Python 3.11+ e uv. O download completo tem cerca de 500 MB (3 GB extraídos). Marcas é o ativo pesado: 19 milhões de despachos, ~1,5 min de silver e 6 GB de RAM.

Instale as dependências
git clone https://github.com/Jaimenms/badepi-dashboard.git
cd badepi-dashboard
uv sync
Bronze — baixe e extraia (todos os ativos, ou só os desejados com -s)
uv run badepi bronze
uv run badepi bronze -s patentes -s pi_genero
Silver — transforme em parquet
uv run badepi silver                  # patentes, marcas, desenho_industrial, indicacao_geografica
uv run badepi silver -s marcas --force
Gold — gere os JSON dos painéis (inclui o comparativo da página inicial e este guia) e sirva o site
uv run badepi gold
python -m http.server -d docs 8000      # abra http://localhost:8000
Atalho: uv run badepi all executa bronze → silver → gold. Use --force para refazer uma camada já construída. A variável BADEPI_DATA_DIR muda a pasta dos dados. Publicação: push na main dispara o workflow que publica docs/ no GitHub Pages.
Modelo de dados

As tabelas silver de cada ativo

Os quatro ativos seguem o mesmo esqueleto, sempre ligado pela chave no_pedido: um fato <prefixo>_deposito (1 linha por pedido, com título/nome, datas, via, origem pelo primeiro depositante e a classificação principal), uma derivada <prefixo>_situacao (situação atual, marcos do processo, vigência e tempos), as tabelas N:1 (depositantes, inventores/autores, despachos, classes, PCT, prioridades, gênero) e as dimensões (códigos de despacho com evento, países, UFs, campos tecnológicos). Datas são datetime64[ms]; vazios são nulos; inteiros usam tipos nullable (Int8/Int16/Int32).

Pandas

Consultando a silver

Os arquivos são parquet comuns: qualquer ferramenta lê. Com pandas, o helper read_parquet do pacote cuida dos datasets particionados (ptn_despacho e mrc_despacho, por ano de publicação) e preserva os tipos nullable. O padrão é sempre o mesmo: fato ⨝ situação pela chave, depois os joins N:1 que a análise pedir.

from badepi.ioutil import read_parquet

def fato(ativo, prefixo):
    S = f"data/silver/{ativo}"
    dep = read_parquet(f"{S}/{prefixo}_deposito.parquet")
    sit = read_parquet(f"{S}/{prefixo}_situacao.parquet")
    return dep.merge(sit, on="no_pedido")

ptn = fato("patentes", "ptn")            # 702 mil linhas
mrc = fato("marcas", "mrc")              # 5,15 milhões
di  = fato("desenho_industrial", "di")   # 158 mil
ig  = fato("indicacao_geografica", "ig") # 254

Patentes

# tempo mediano até a concessão por campo tecnológico (concessões desde 2020)
dim = read_parquet("data/silver/patentes/dim_campo_tec.parquet")
rec = ptn[ptn.dt_concessao >= "2020-01-01"]
(rec.groupby("campo_tec_principal").anos_ate_concessao.median().rename("mediana_anos")
    .to_frame().join(dim.set_index("campo_tec")).sort_values("mediana_anos"))

# despachos de 2024 em diante (lê só as partições necessárias) e inventores de um pedido
desp = read_parquet("data/silver/patentes/ptn_despacho", filters=[("ano_publicacao", ">=", 2024)])
inv  = read_parquet("data/silver/patentes/ptn_inventor.parquet")
inv[inv.no_pedido == "102012000050"][["no_ordem", "nome", "uf", "cidade"]]

Marcas

# taxa de registro por classe de Nice, pedidos de 2015 a 2019
m = mrc[mrc.ano.between(2015, 2019)]
(m.groupby("classe_nice_principal").agg(pedidos=("no_pedido", "size"), registrados=("dt_concessao", lambda s: s.notna().sum()))
  .assign(taxa=lambda t: t.registrados / t.pedidos).sort_values("taxa", ascending=False))

# oposições: pedidos com notificação de oposição (evento 'oposicao') por UF do depositante

Método

Como as derivações são calculadas

Eventos e situação (todos os ativos)

Cada código de despacho da RPI é mapeado para um evento (depósito, publicação, oposição, exigência, parecer, deferimento, indeferimento, concessão/registro, arquivamento, desarquivamento, restauração, extinção, prorrogação, desistência, recurso, recurso provido/negado, nulidade, anulação, transferência/alteração, petição, administrativo…). O mapeamento de cada ativo está em silver/<ativo>.py e o resultado por código na tabela dim_despacho.

A situação de um pedido usa a última data de cada tipo de evento, nesta ordem (silver/common.py, função derive_situacao):

  1. Houve concessão/registro? Então é Anulada se houve anulação posterior; Extinta se a última extinção é posterior à última restauração; senão Concedida.
  2. Numeração anulada (patentes, código 15.21) sem publicação, deferimento nem concessão → Numeração anulada: o depósito nunca se efetivou. Esses pedidos ficam fora do ciclo de vida, do funil e do estoque sem decisão, e os KPIs trazem o total de pedidos efetivos ao lado do bruto.
  3. Desistência ou retirada posterior a qualquer decisão → Retirada.
  4. Indeferimento não revertido por recurso provido nem seguido de deferimento → Indeferida.
  5. Arquivamento não revertido por desarquivamento/restauração nem seguido de deferimento → Arquivada.
  6. Deferimento sem concessão → Deferida.
  7. Caso contrário → Em andamento.

A tabela de situação guarda também os marcos (primeira publicação, oposição, exigência, parecer, deferimento, indeferimento, concessão, último arquivamento, extinção, desistência, última prorrogação), a primeira decisão de encerramento, o fim da vigência legal, a flag prazo_expirado e os tempos anos_ate_concessao e anos_ate_decisao. "Vigente" = concedida/registrada, não extinta e dentro do prazo legal.

Particularidades por ativo

  • Patentes. Vigência de 20 anos (PI e CA) ou 15 (MU) contados do depósito. Natureza pelo prefixo do número (PI/10/11/12 → PI; MU/20/21/22 → MU; C/13 → CA). Via PCT: prefixo 11/21, presença em ptn_pct ou despachos 1.1/1.3. Campo tecnológico principal = campo OMPI da IPC de ordem 1. Os 304 códigos de despacho vêm com descrição na fonte.
  • Marcas. Sem prazo máximo (registro de 10 anos prorrogável indefinidamente): "vigente" = registrada sem extinção publicada. O BADEPI traz só o código do despacho (DESP### até 2013, IPAS### desde então, em tabelas diferentes); os decisivos foram identificados em publicações da RPI — publicação para oposição (003/IPAS009), oposição (IPAS423), exigência de mérito (IPAS142/136), deferimento (351/IPAS029), registro (400/IPAS158), arquivamento por falta de pagamento (150/IPAS157) ou de cumprimento de exigência (IPAS139), indeferimento (100/IPAS024), recurso (IPAS360/237/235), extinção (IPAS161), petições (IPAS270/271/428) — e os demais ficam como "outros". Classe principal = primeira classe de Nice.
  • Desenhos industriais. Vigência máxima de 25 anos (10 + 3 × 5). Não há publicação antes do registro (só exame formal). Códigos antigos vêm com descrição; os do sistema novo (fim de 2023) foram inferidos pela cronologia: 860 depósito, 158 registro, 870 prorrogação, 136 exigência, 139 arquivamento, 270 petição deferida, 1214/1233/1252 trâmite via Haia. Numeração BR 31 = via Acordo de Haia; BR 32 = dividido (provável). Classe principal = classe de Locarno de ordem 1.
  • Indicações geográficas. Registros não expiram. Espécie atual (tipo_atual) incorpora alterações de IP para DO. Classificação OMPI (agroalimentar, vinhos e destilados, artesanato, serviço, outros) da fonte.
  • PI e Gênero. Sexo provável pelo primeiro nome (Censo 2022) de inventores (patentes) e depositantes pessoa física residentes (patentes, marcas, desenhos); a fonte não traz a ordem, só uma linha por menção.

Origem, categoria e nomes

  • Origem do pedido: país, UF, município e categoria do depositante de ordem 1 (regra do manual do BADEPI). Residente = país BR.
  • Categoria do depositante: expressões regulares sobre o nome normalizado (universidade, instituto de pesquisa, governo, empresa) combinadas com o tipo de pessoa (F/J) informado para residentes. Pedidos em sigilo chegam sem nome → "não identificado".
  • Nome normalizado (nome_norm): caixa alta, sem acentos nem pontuação; agrupa grafias diferentes do mesmo titular nos rankings.

Ciclo de vida e grafo de transições

O ciclo de vida calcula, para cada pedido, o estado a cada meio ano decorrido desde o protocolo (depositado → publicado/em exame → vigente, ou indeferido/arquivado/retirado → extinto ou expirado), usando só os pedidos já observáveis naquele ponto. O grafo de transições conta, dentro de cada pedido, os pares de despachos consecutivos (a → b) por ano de depósito; os códigos mais frequentes viram nós e os demais são somados em "OUTROS".

Problemas conhecidos da fonte (v12)

  • Patentes: DT_PEDIDO_ORIGEM em prioridades repete o número da prioridade (datas ficam nulas); seis pedidos com número inválido (erro1…, 0); datas-sentinela (0001-01-01, 2099-01-01, 1111-11-11) tratadas como nulas; ~6% dos pedidos sem classificação IPC; cerca de 23 mil pedidos com "numeração anulada" (15.21) que nunca se efetivaram, tratados como situação própria.
  • Marcas e desenhos: despachos sem descrição (ver acima); em marcas, o campo NO_ORDEM do depositante vem vazio na maioria das linhas (tratado como ordem 1).
  • Encoding misto em todos os ativos: a maioria das tabelas está em cp1252, algumas em UTF-8, e há linhas isoladas no outro encoding; a leitura decodifica linha a linha.
  • Pedidos ainda em sigilo (18 meses) não têm nome de depositante nem título.
